# Aster Desktop — Security and Privacy Requirements

**Status:** Normative baseline

**Applies to:** Source, tests, local data, CI, packages, installers, updates, and documentation

**Last updated:** 2026-07-13

**Implementation status:** These are mandatory controls, not claims of implementation or verification.

## 1. Security objectives

MVP v2 protects each provider credential, prevents cross-provider confusion and model/imported content from becoming executable authority, limits desktop privileges, keeps local conversation and usage handling explicit, and makes release integrity demonstrable. Security claims require evidence; absence of a finding is not proof of a control.

Security priorities are:

1. API-key confidentiality and strict backend custody.
2. Integrity of the application, requests, local history, and release artifacts.
3. Safe rendering and parsing of hostile provider/imported content.
4. Least-privilege IPC, OS permissions, networking, and filesystem access.
5. Availability through bounded processing, cancellation, recovery, and safe failures.
6. User knowledge and control over external processing and plaintext export.

## 2. Data handling policy

| Data class                   | Examples                                                                                   | Storage                                                  | Permitted transmission                                                  | Logging                         |
| ---------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------- |
| Secret                       | Provider API keys and authorization headers                                                | Separate provider-scoped Windows credential targets only | Matching provider over validated HTTPS from Rust                        | Never                           |
| Sensitive user content       | Prompts, responses, titles, imported/exported conversations                                | User-scoped SQLite; explicit plaintext export            | Selected identified provider after user send; user-selected export path | Never                           |
| Sensitive financial metadata | Exact DeepSeek balance response and observation time                                       | Rust memory for current session only                     | Bounded status DTO to main webview                                      | Never                           |
| Internal usage metadata      | Message times, pinned provider/model/profile, disjoint token observations, advisory budget | User-scoped SQLite                                       | Safe bounded Usage DTO only; budget is never sent to a provider         | No content or direct identifier |
| Safe application errors      | Stable code, bounded user message, retryable flag                                          | Not persisted by Aster v2                                | IPC to the main webview only                                            | No application logging          |
| Public application data      | Static UI copy, schema name/version                                                        | Package/configuration                                    | As needed                                                               | Allowed                         |

Local SQLite history is not claimed to be encrypted by the application. Windows user-account and filesystem protections are relied upon in v2, and the UI must describe local persistence accurately. Device compromise, an already-unlocked hostile user session, and provider-side retention are residual risks rather than controls the client can eliminate.

| `SEC-049` | Local usage observations **MUST** contain only a catalog-valid provider/model, canonical UTC time, canonical idempotent opaque operation identity, partial flag, and disjoint optional `inputTokens`, `cachedInputTokens`, `outputTokens`, and `totalTokens`. Schema constraints and Rust read validation **MUST** reject malformed/tampered identity, time, pair, token, arithmetic, or partial-state rows before lexical seven-day filtering or aggregation. Exactly one partial marker is created immediately before networking for each validated send; authoritative final usage fills it once, while cancellation/failure/missing/malformed usage leaves it partial. ## 4. Verification environments

| Environment        | Allowed secrets                                 | External provider                       | Security evidence value                        |
| ------------------ | ----------------------------------------------- | --------------------------------------- | ---------------------------------------------- |
| Unit/component     | None; fake sentinels only                       | No                                      | Pure logic and rendering controls              |
| Integration        | Isolated fake credential target; fake sentinels | Local fake SSE server                   | IPC, credential, storage, parser, cancellation |
| Browser demo       | None                                            | No                                      | Visual/accessibility behavior only             |

| Release validation | No embedded secret                              | Network only if explicit test plan      | Package, policy, SBOM, signature, provenance   |

A real provider key may be supplied only by a protected CI secret or user at runtime to an explicitly selected live-contract test. It must be masked, minimally scoped if the provider supports scope, and never available to untrusted pull-request code.

## 5. Security gate policy

Each required control reports `PASS`, `FAIL`, or `NOT RUN` with a source revision and evidence location. `NOT RUN` includes unavailable tools, unavailable Windows host, missing signer, missing SBOM, or missing evidence. For a production release, any required `FAIL` or `NOT RUN` blocks the release.

An engineering MVP build may be delivered for local evaluation with explicitly reported production-only gates not run, particularly installer signing, but it may not be called signed, hardened, production-ready, or generally distributable. Runtime controls protecting credentials and data are not waivable merely because the build is an engineering build.
